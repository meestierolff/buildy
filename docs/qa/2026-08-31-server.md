## Fixed: delayed Stripe checkout retries changed request parameters

`StripePaymentProvider.createCheckout` previously computed `expires_at` from
`Date.now()` on every invocation, while `OrderService` correctly reused the
same provider idempotency key for a reserved order. A retry after a lost response
or failed database write therefore sent different parameters under the same
key. Stripe rejects that mismatch, leaving the existing reservation unable to
recover through the intended retry path.

The service now derives one deadline from the immutable persisted quote expiry
plus 35 minutes. The adapter passes that exact deadline on every attempt. This
works across function instances without process-local caching and preserves
Stripe's 30-minute minimum with five minutes of transport margin for any first
attempt made while the quote is valid. With the existing maximum 30-minute quote
TTL, the initial Checkout deadline is at most 65 minutes away. No schema or
migration change was needed.

Regressions cover:

- A provider-created session whose first response is lost, recovered 28 minutes
  later by a fresh adapter instance; the fake Stripe boundary rejects any
  parameter or idempotency-key difference.
- A failed session-persistence write followed by a delayed retry using a renewed
  client UUID and quote freshness fields; the original reservation deadline and
  all provider input remain identical.

Provider contracts verified against primary documentation:
[Stripe idempotent requests](https://docs.stripe.com/api/idempotent_requests) and
[Checkout Session creation](https://docs.stripe.com/api/checkout/sessions/create).
